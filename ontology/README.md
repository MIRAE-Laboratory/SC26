# 과학 계산과 AI의 검증 온톨로지

SC26 지식그래프(`data/`)에서 "검증"에 해당하는 부분을 추려 따로 구성한 온톨로지임. 심층 요약 2 "기준이 '돌아간다'에서 '검증된다'로 옮겨 감"의 범위. 검증 수단이 어떤 대상의 어떤 실패를 잡거나 놓쳤는지를 다룸.

큐레이션된 지식그래프를 먼저 만들고, 그 안에서 쓸모 있는 것만 골라 온톨로지로 올리는 접근을 시험한 기록이기도 함.

## 파일

| 파일 | 내용 |
|---|---|
| `verification.yaml` | 원본. 역량 질문, 대상·실패 유형·수단·자산의 정의와 위계, 검증 사례, 구성 과정 기록 |
| `verification.ttl` | 같은 내용의 OWL(Turtle). `tools/build_ontology.py`가 만듦 |
| `verification.json` | 규칙을 적용한 도출 결과. 뷰어의 "검증 온톨로지" 화면이 읽음 |

## 방법

1. 역량 질문 여덟 개를 먼저 정함(아래).
2. 지식그래프에서 검증 범주의 문제·기법 개념과 연결된 발표 97건을 읽고, 수단이 실패를 잡았는지 놓쳤는지를 보고한 발표를 사례로 고름.
3. 클래스 넷을 정의함: 검증 대상 23, 실패 유형 21, 검증 수단 36, 전제 자산 17. 수단에는 결정론 여부, 보증 수준, 전제 자산, 적용 대상을 붙임.
4. 발표를 검증 사례 51건(수단, 대상, 실패, 결과)과 관찰 6건(수단 없이 보고된 실패)으로 다시 적음. 근거 발표는 39건임.
5. 제약을 검사함: 사례의 수단은 그 대상에 적용 가능해야 하고, 범위 보증 수단은 결정론적이어야 함.
6. 규칙 여덟 개를 적용해 질문에 답함.

## 구조

- `VerificationCase` —usesMethod→ `VerificationMethod`, —onTarget→ `Target`, —concernsFailure→ `FailureMode`, outcome(caught, partial, missed, used), —evidencedBy→ 지식그래프의 발표
- `VerificationMethod` —requires→ `Asset`, —appliesTo→ `Target`, deterministic, assuranceLevel(sample, scope, runtime, judgment), skos:closeMatch → 지식그래프의 개념
- 위계는 skos:broader. 수단과 대상의 적용 범위는 상위 항목에서 하위 항목으로 물려받음.

## 역량 질문과 답

**Q1. 컴파일과 실행 성공만 확인하면 어떤 실패 유형을 놓치는가**

실패 유형 4가지: 실행은 되지만 전문가 관례를 어김, 조용히 틀린 결과, 결과의 과학적 의미가 바뀜, 정상으로 보이는 학습 실패

**Q2. 어떤 대상의 어떤 실패가 보고됐는데 그것을 잡은 수단은 보고되지 않았는가**

8개 조합: 벤치마크 종합 점수 × 측정이 틀린 값을 냄 (수단 보고 없음); LLM의 과학적 제안(설계안) × 근거 없는 답과 위조 인용 (수단 보고 없음); 병렬 통신 프로그램 × 교착과 경합 (채택만 보고됨); 대규모 학습 작업 × 정상으로 보이는 학습 실패 (채택만 보고됨); 대규모 학습 작업 × 조용한 데이터 손상 (채택만 보고됨); 하드웨어 결함 거동 × 조용한 데이터 손상 (일부만 잡음); 신경망 대리모델 × 물리·도메인 제약 위반 (일부만 잡음); LLM의 과학적 제안(설계안) × 물리·도메인 제약 위반 (일부만 잡음)

**Q3. 한 가지 수단에만 기대고 있는 실패 유형은 무엇인가**

12개: 크래시와 실행 실패 ← 퍼징; 실행은 되지만 전문가 관례를 어김 ← 결정론적 검사와 LLM 평가의 결합; 결과의 과학적 의미가 바뀜 ← 사람이 검토한 명세와의 대조; 물리·도메인 제약 위반 ← 모델 검사(입력을 기호로 둠); 예측 오차의 누적 ← 실측과의 잔차 감시; 조용한 데이터 손상 ← 물리 기반 체크섬; 교착과 경합 ← 모델 검사(입력을 기호로 둠); 성능 회귀와 노드 간 편차 ← 상시 벤치마크와 회귀 시험; 허용되지 않은 행동의 실행 ← 모델 밖의 결정론적 실행 검사와 중재; 불완전하거나 잘못된 입력으로 실행 ← 스키마로 입력을 확인하고 실행을 막음; 근거 없는 답과 위조 인용 ← 모델 밖의 결정론적 실행 검사와 중재; 악용 가능한 취약점 ← 퍼징

**Q4. 어떤 수단이 놓친 실패를 다른 어떤 수단이 잡았는가**

보완 관계 17쌍. 예: 컴파일과 실행 성공 확인 → 결정론적 검사와 LLM 평가의 결합 (AI가 생성·변환한 코드 × 실행은 되지만 전문가 관례를 어김); 컴파일과 실행 성공 확인 → 사람이 검토한 명세와의 대조 (워크플로(생성물과 유지보수 수리) × 조용히 틀린 결과); 비트 단위 재현 관문 → 결함 주입(검증 수단과 내성의 시험) (AI가 생성·변환한 코드 × 조용히 틀린 결과); 비트 단위 재현 관문 → 결정론적 검사와 LLM 평가의 결합 (AI가 생성·변환한 코드 × 조용히 틀린 결과)

**Q5. 어떤 자산 하나를 갖추면 가장 많은 검증 수단을 쓸 수 있게 되는가**

사람이 검토한 명세와 수용 기준: 실패 유형 5종; 시험 입력과 시나리오 모음: 실패 유형 4종; 검증용으로 뽑아낸 작은 모델: 실패 유형 3종; 허용 행동 정책과 값의 출처 레이블: 실패 유형 3종; 전문가의 검토 시간: 실패 유형 2종

**Q6. 시험한 입력에서만 성립하는 보증에 머물러 있는 곳은 어디인가**

11개 조합: 과학 응용 코드 × 크래시와 실행 실패; 과학 응용 코드 × 악용 가능한 취약점; AI가 생성·변환한 코드 × 실행은 되지만 전문가 관례를 어김; AI가 생성·변환한 코드 × 조용히 틀린 결과; 대규모 학습 작업 × 조용한 데이터 손상; 하드웨어 결함 거동 × 조용한 데이터 손상; 컴파일러·도구 사슬 × 조용히 틀린 결과; 신경망 대리모델 × 물리·도메인 제약 위반; LLM의 과학적 제안(설계안) × 물리·도메인 제약 위반; 전력 계측 × 측정이 틀린 값을 냄; 하드웨어 계수기 × 측정이 틀린 값을 냄

**Q7. 결정론적이지 않은 판정에만 기대는 곳은 어디인가**

4개 조합: 과학 응용 코드 × 크래시와 실행 실패; 과학 응용 코드 × 악용 가능한 취약점; AI가 생성·변환한 코드 × 실행은 되지만 전문가 관례를 어김; LLM의 과학적 제안(설계안) × 물리·도메인 제약 위반

**Q8. 한 대상에서 통한 수단을 아직 쓰지 않은 다른 대상에 옮겨 볼 만한 곳은 어디인가**

2개: LLM의 과학적 제안(설계안)의 근거 없는 답과 위조 인용 ← 모델 밖의 결정론적 실행 검사와 중재 (에이전트의 답과 인용에서 잡음); 병렬 통신 프로그램의 교착과 경합 ← 모델 검사(입력을 기호로 둠) (과학 응용 코드에서 잡음)

## 결과의 평가

### 새로 나온 것

- 대규모 학습 작업의 "정상으로 보이는 실패"는 잡았다고 보고한 수단이 하나도 없음. 실행 확인은 놓쳤고, 기록과 재생은 제안 단계이며, 다른 발표는 같은 실패를 겪었다고만 보고함. 이 범위에서 가장 뚜렷한 빈칸임.
- 말단 실패 유형 18개 가운데 12개는 잡았다고 보고된 수단이 한 가지뿐임. 고찰에서는 "단일 방어선은 버티지 못함"을 사례 셋으로 적었으나, 구조로 보면 단일 방어선이 예외가 아니라 일반적인 상태임.
- 전제 자산별로 보면 "사람이 검토한 명세"가 가장 많은 실패 유형(5종)을 잡는 수단들의 전제임. "기준 출력"은 수단 셋이 요구하지만 잡은 실패는 "조용히 틀린 결과" 한 종류뿐임. 적용 제안에서는 기준 출력의 정비를 앞세웠는데, 넓이로는 명세와 수용 기준을 적어 두는 일이 더 큼.
- AI가 생성·변환한 코드의 조용한 오류에는 수단 일곱 가지가 쓰였으나 모두 시험한 입력에서만 성립하거나 판단에 의존하는 보증임. 정한 범위 전체를 보증하는 수단(계약 검사, 모델 검사)은 사람이 쓴 수치 라이브러리와 응용 코드에서만 보고됨.
- 옮겨 볼 만한 조합 둘이 나옴. 응용 코드에서 교착과 경합을 잡은 모델 검사를 병렬 통신 프로그램에, 에이전트의 위조 인용을 막은 모델 밖 실행 검사를 LLM의 과학적 제안에 적용하는 것임.

### 이미 고찰에 있던 것

- 컴파일과 실행 성공 확인이 네 가지 실패 유형을 놓친다는 것(Q1)은 심층 요약의 "실행 성공은 다섯 가지 방식으로 틀릴 수 있음"과 같은 내용임.
- LLM 판정, 프롬프트 지시, 계보 기록이 놓친 것을 다른 수단이 잡았다는 것(Q4의 대부분)도 고찰과 쟁점 대조표에 이미 있음.

### 한계

- 사례 51건, 근거 발표 39건의 작은 온톨로지임. "보고 없음"은 공개 초록 요약에 없다는 뜻이며 그런 연구가 없다는 뜻이 아님.
- 대상, 실패 유형, 결과의 판정은 한 사람이 초록 요약을 읽고 내린 것임. 다른 사람이 하면 달라질 수 있음.
- 도출 규칙은 파이썬으로 구현했고 OWL 추론기는 쓰지 않았음. Turtle 파일은 문법 검사기로 확인하지 못했음.

## 지식그래프에서 온톨로지로: 구성 과정의 기록

**올린 것.** 지식그래프의 기법 개념 가운데 검증 수단으로 올린 것은 kg 항목에 적은 16개임. 문제 개념은 그대로 올리지 않고 "대상"과 "실패 유형"으로 나눠 다시 정의함.

**나눈 것.**

- 지식그래프의 "결함 주입·퍼징"은 한 개념이었으나, 취약점을 찾는 퍼징과 검증 수단 자체를 시험하는 결함 주입은 전제 자산과 잡는 실패가 달라 둘로 나눔.
- 지식그래프의 "출력·동작 동등성 시험"은 기준 출력 비교, 비트 단위 재현, 독립 시뮬레이터 비교, 변형 관계 검사로 나눔. 보증 수준과 필요한 자산이 서로 다름.
- 지식그래프의 "실행 기록·출처 로깅"은 실행 증거 남기기(재생 가능)와 계보 기록의 확인(읽기만 함)으로 나눔. 뒤쪽은 적용 범위 이탈을 놓친 사례가 있음.
- 지식그래프의 "정형 검증과 모델 검사"는 모델 검사, 연역 검증, 계약 검사로 나눔.

**새로 만든 것.**

- 실패 유형 클래스 전체. 지식그래프에는 실패 유형이 없어 문제 개념과 발표 요약 문장 속에 흩어져 있었음.
- 전제 자산 클래스 전체. 지식그래프에서는 적용 제안의 "선행 조건" 문장으로만 존재했음.
- 검증 사례(수단, 대상, 실패, 결과)라는 4항 관계. 지식그래프의 "발표가 기법을 제안함"으로는 잡았는지 놓쳤는지를 표현할 수 없었음.
- 수단의 속성인 결정론 여부와 보증 수준.
- 기준선 수단 "컴파일과 실행 성공 확인"과 "프롬프트 지시만", "LLM 판정". 발표가 제안한 것이 아니라 비교 대상으로 등장해 지식그래프에는 개념이 없었음.

**올리지 않은 것.** 검증·시험 범주의 기법 가운데 "실패 원인 분류와 자기 개선", "위험 지향 계약", "보증 문제로서의 프라이버시", "확률적 오차 한계 분석"은 실패를 잡는 수단이 아니라 분류, 계약, 분석 틀이어서 올리지 않음. 검증과 무관한 발표(범위 안 97건 가운데 사례로 쓰지 않은 것)는 제외함.

**지식그래프의 맹점과 순서의 효과.**

- 지식그래프의 "문제 / 기법 / 대상" 구분에는 "결과(잡음, 놓침)"를 담을 자리가 없었음. 온톨로지에서 가장 쓸모 있는 정보가 여기서 나옴.
- 지식그래프의 "대상 시스템"은 무엇에 적용했는지(예를 들어 리더십급 시설)였고, 무엇을 검증하는지(예를 들어 변환된 코드)가 아니었음. 검증 대상을 따로 정의해야 했음.
- 처음부터 온톨로지를 설계했다면 검증 수단의 위계는 교과서 분류(정적, 동적, 정형)를 따랐을 것임. 발표를 먼저 모은 덕에 "모델 밖 실행 검사", "적용 범위 정보", "실행 증거"처럼 교과서에 없는 수단이 주요 항목으로 들어감.

## 다시 만들기

```bash
pip install pyyaml
python tools/build_ontology.py
```

`verification.yaml`을 고친 뒤 다시 돌리면 OWL 파일과 도출 결과가 갱신됨. 제약 위반이 있으면 목록을 내고 멈춤.
